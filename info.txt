# DESIGN SYSTEM (build before pages)
Create a shared system and reusable components so every page feels like one product: typography, spacing, colors, borders, shadows, radii, buttons, cards, badges, inputs, dialogs, navigation, section headers, code blocks, tables, markdown, status indicators.
- Light mode: layered neutrals, subtle accents, strong contrast, soft borders, restrained shadows.
- Dark mode: NOT black + white text. Use stepped surfaces (page -> section -> card -> elevated -> interactive), tasteful accents, dimensional but not neon. One consistent palette across both modes.
- Motion (Framer Motion / Motion for React): page transitions, section reveals, nav, hover, modals/drawers, diagram interaction. Subtle and fast. No heavy parallax, constant movement, bouncing, giant animated backgrounds, or per-element animation. Respect prefers-reduced-motion.
- Hover: project cards lift, borders transition, thumbnails scale slightly, links animate underline, tech nodes respond, GitHub cards reveal useful metadata. Don't glow everything.
- Responsive: design deliberately for 320, 375, 390, 768, 1024, 1440+. Mobile layouts designed independently where needed. No horizontal overflow.
- Accessibility: keyboard navigation, visible focus, semantic HTML, ARIA only where needed, sufficient contrast, accessible forms and dialogs.

# V2 - ENGINEERING UPGRADE (only after V1 is stable)
1. CI/CD: GitHub Actions on PR: install -> lint -> typecheck -> unit -> E2E -> build. Deploy only after required checks pass. Don't claim deployment automation unless the workflow actually deploys.
2. Testing: unit tests (business logic/utilities), integration tests (Supabase where practical), Playwright E2E covering: visitor flow (home -> projects -> case study -> GitHub); admin flow (login -> create -> draft -> publish -> edit -> verify public page); security (anon can't reach admin, anon can't read drafts, non-admin can't modify content). Include RLS tests.
3. Security: headers, CSP, secure cookies, server-side authorization, input validation, rate limiting, protected privileged routes, secret protection. Nothing decorative.
4. GitHub sync engine: scheduled + manual sync, retries, rate-limit awareness, sync status, error logging, idempotent upserts, last-successful-sync, results recorded in `github_syncs`. Failed syncs must be visible to the admin. Make it genuinely incremental (use timestamps/sync state, skip unchanged data) or don't call it incremental. Scheduled sync only if scheduling infrastructure is configured.
5. Observability: use an established error-monitoring tool; track server errors, failed syncs, failed admin operations, unexpected API errors. Don't build a platform.
6. Performance: measure Lighthouse, Core Web Vitals, server response time, query performance, bundle size; fix real bottlenecks only (Server Components, caching, image optimization, dynamic imports, pagination, indexes where justified). No "highly optimized" claims without data.
7. Database engineering: review indexes, FKs, query patterns, RLS performance, N+1s with EXPLAIN where useful. No blind indexes.
8. Caching: only with measurable benefit and correct invalidation; prefer built-in Next.js/Supabase mechanisms over Redis unless justified.
9. Error handling: loading, error, empty, and success states on key flows; admin can tell succeeded / failed / partially succeeded; no swallowed errors.
10. Validation: schema validation (e.g. Zod) for admin forms, project data, article metadata, GitHub responses, analytics payloads. Never trust external data.
11. Docs: ARCHITECTURE.md (system, frontend, DB, auth, RLS, GitHub, analytics, deployment, testing), SECURITY.md (auth, authorization, RLS, secrets, analytics privacy, GitHub credentials, security testing), DECISIONS.md (non-trivial decisions only, e.g. why Supabase, PostgreSQL, RLS, Next.js, server-side sync, no Redis, Markdown, JSONB diagrams). Must match the actual implementation.
12. Case study upgrades for selected projects: real architecture diagram, data flow, security, performance (measured), testing, tradeoffs, failure modes, lessons.
13. Interview Notes per major project, with answers grounded in the actual implementation (e.g. why PostgreSQL, how RLS protects data, how sync avoids duplicates, how auth differs from authorization). No generic textbook answers.
14. Metrics: only real ones (coverage, latency, load-test, repo activity, Lighthouse); otherwise "Not measured" or omit.
15. Deployment docs: describe only the real deployment pipeline; don't claim AWS/Vercel/etc. unless used.
